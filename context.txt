# CRM AI — Complete Project Context

## 1. Project Identity

Project name:
AI-Powered CRM Lead Prioritization & Next-Best-Action System

Project type:
Explainable machine-learning sales intelligence platform.

Primary goal:
Analyze CRM lead information, customer interactions, engagement history, and opportunity attributes to:
- calculate lead-quality / conversion scores
- rank leads for sales follow-up
- recommend the next best sales action
- explain why a lead received its score and recommendation
- provide pipeline analytics
- allow sales users to override AI recommendations
- capture human feedback for later model evaluation/improvement

This is intended to become:
1. A hackathon project
2. A serious ML portfolio project
3. A resume project
4. A project that can be defended technically in interviews

Important:
Do not build a fake "AI dashboard" where an LLM simply invents scores.
The core intelligence must be measurable, reproducible, explainable, and evaluated.

---

## 2. Core Problem

Sales teams cannot manually evaluate every lead with equal depth.

The system should help sales representatives focus on stronger opportunities while showing evidence for every recommendation.

The core questions are:

1. How promising is this lead?
2. Why did the system give it this score?
3. What should the salesperson do next?
4. Does the salesperson agree with the recommendation?
5. What happened after the recommendation?

## 5. ML Architecture

The ML system should be the real intelligence of the project.

Do not make the LLM the primary scoring mechanism.

Preferred flow:

CRM data
    ↓
Feature engineering
    ↓
ML model
    ↓
Conversion probability
    ↓
Lead score
    ↓
SHAP explanation
    ↓
Next-best-action rules / decision engine
    ↓
Optional LLM natural-language explanation

The LLM, if used, is optional and should primarily improve natural-language presentation rather than inventing the underlying score.

---

## 6. Models

Start with a baseline and compare multiple models.

Candidate models:
- Logistic Regression
- Random Forest
- Gradient Boosting

Do not automatically assume one is best.

Evaluate based on:
- ROC-AUC
- Precision
- Recall
- F1
- Confusion Matrix
- Probability calibration
- Ranking metrics where appropriate

For this tabular CRM problem, avoid unnecessary deep learning.

A simple interpretable model may outperform a more complex model in terms of defensibility.

---

## 7. Lead Scoring

The ML model should estimate conversion probability.

Example:

conversion_probability = 0.87

Then:

lead_score = 87 / 100

Do not confuse:
- model probability
- lead score
- recommendation confidence

They are related but not automatically identical.

## 10. Feature Engineering

Raw CRM fields should be transformed into useful features.

Examples:

emails_opened / emails_sent
    ↓
email_open_rate

emails_clicked / emails_opened
    ↓
click_rate

calls_answered / calls_attempted
    ↓
call_response_rate

days_since_last_contact
    ↓
recency signal

pricing_page_visits
    ↓
purchase-intent signal

Feature categories should include:

1. Engagement features
2. Intent features
3. Recency features
4. Opportunity features
5. Account/profile features
6. Interaction-history features

Avoid leakage.

Do not use information that would only become known after the prediction point.

## 12. Explainable AI

Use SHAP for feature-level explanations.

Example:

Lead Score: 87

Positive factors:
- Demo requested: +18
- Pricing visits: +12
- Email engagement: +10
- Deal value: +6

Negative factors:
- No recent reply: -5
- Low recency: -4

The dashboard should communicate:

"High conversion potential because the lead requested a demo, repeatedly visited the pricing page, and engaged with recent emails. Lack of recent phone engagement reduced the score."

Important:
The numerical/model explanation should come from the model explainability layer, not be invented by an LLM.

## 13. Next-Best-Action Engine

The recommendation engine answers:

"What should the salesperson do next?"

Possible actions:
- CALL
- EMAIL
- DEMO
- NURTURE
- REVIEW

Start with transparent deterministic rules.

Example:

Score >= 80:
- Demo requested → DEMO
- Otherwise → CALL

Score 60–79:
- High email engagement → EMAIL
- Strong recent interaction → CALL

Score 40–59:
- NURTURE

Score < 40:
- Long-term NURTURE

These are starting rules only. They should eventually consider:
- lead score
- intent
- engagement
- recency
- opportunity stage
- previous communication
- customer preferences
- action history

Do not make recommendations opaque.

---

## 14. Recommendation Confidence

The UI may show recommendation confidence, but do not automatically equate:
- model probability
with
- recommendation confidence

Define confidence properly.

Example:

Recommendation:
CALL

Confidence:
91%

Reasons:
- high recent engagement
- recent email response
- no demo request
- high opportunity value

## 15. Human-in-the-Loop

Human override is required.

Flow:

AI recommendation
    ↓
Salesperson
    ↓
Accept OR Override
    ↓
If override:
    choose different action
    add reason
    ↓
save feedback

Example:

AI:
CALL

Sales rep:
EMAIL

Reason:
"Customer requested email communication."

Store:
lead_id
original_action
override_action
reason
timestamp

Do not automatically retrain the model during the initial build.

Store feedback for later evaluation and potential future retraining.

---

## 16. Evaluation

Model evaluation must be real.

Classification metrics:
- ROC-AUC
- Precision
- Recall
- F1
- Confusion Matrix

Also evaluate ranking/business usefulness:

- Precision@K
- Recall@K
- Top-K conversion rate
- Lift
- Conversion rate by score bucket
- Calibration

Example:

Top 10% highest-scored leads
    ↓
Conversion rate: 31%

All leads
    ↓
Conversion rate: 8%

This demonstrates whether ranking is useful to sales teams.

---

## 17. Data Split

Use proper train/validation/test methodology.

Prevent:
- data leakage
- target leakage
- duplicate leakage

If interaction history is time-dependent, consider time-aware splitting rather than blindly random splitting.

## 32. Engineering Principles

1. Build the ML system first, not the dashboard first.
2. Establish a baseline before claiming ML improvement.
3. Prevent data leakage.
4. Keep explanations tied to actual model behavior.
5. Keep recommendations transparent.
6. Separate model probability from recommendation confidence.
7. Keep human override available.
8. Store feedback instead of pretending automatic learning exists.
9. Keep FastAPI as the API layer.
10. Keep ML logic separate from API routes.
11. Keep frontend separate from backend intelligence.
12. Prefer measurable evidence over AI-generated claims.
13. Avoid unnecessary infrastructure.
14. Test everything important.
15. Document design decisions and trade-offs.
